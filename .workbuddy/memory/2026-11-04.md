## 后台无法切歌：根因是淡入用 JS setInterval 推音量

**现象**：v0.1.5 之后，后台/锁屏按下一首没反应。

**根因**（`src/bridge/nativePlayer.ts`）：淡入淡出是 JS 用 `setInterval(…, 40)` 每 40ms
推一次 `setVolume` 实现的，而 `playTrack` 里 `await engine.play({ fadeIn: true })` →
`playWithFade` → `await fade(...)`。后台 Chromium 把 `setInterval` 节流到约 1 次/分钟，
一段 1 秒的淡入要跑几十分钟 → 这个 await 永不落地 → 整条切歌链路挂住。
同一机制也会拖死 EOF 自动切歌，不只是手动切。

**决定性证据**：`fade()` 上方原有注释就写着"它挂住会让 engine.play({fadeIn:true})
永不落地 —— 表现为 playbackIntent.phase 卡在 loading、后续切歌与 seek 全被挡住"，
当时只修了"取消时 Promise 不 settle"，没解决"后台节流"。

**修**：音量过渡挪到原生，用 Handler 打步进（不受 WebView 节流影响）。
- `EchoPlaybackService`：新增 `setVolumeRamp(from,to,durationMs)` 与
  `pauseWithFade(durationMs, restoreVolume)`，40ms 一步；`setVolume`/`pause`/`load`
  都会先 `cancelVolumeRamp()`（否则新歌被旧斜坡改音量、淡入被暂停会留半截音量）
- `EchoNativePlayerPlugin`：暴露上面两个方法
- `nativePlayer.ts`：`fade()` 改为一次 `setVolumeRamp` 调用后立即返回；
  `pauseWithFade` 整段交给原生（分三步在 JS 里做同样会被 await 拖住）；
  删掉 `fadeTimer`/`settleFade` 这套 JS 步进机制

**关于"预存 15 首"**：查了 Media3 官方文档，这类问题的标准解法是
`ResolvingDataSource`（just-in-time 解析 URI，播放列表只放 track id，地址在 open 时才解析）。
官方原文就点出"播放列表 20 首要提前取全部地址明显不行，地址还会失效"。
但它的 resolver 跑在**原生**加载线程里，而我们的取链逻辑（酷狗签名/授权）在 JS —— 
要真正零预存，得把 resolver 搬到 Java，或在 resolver 里阻塞等待 JS 回调（latch + 超时）。
这是另一个量级的改造，先记录，未做。

**验证**：101 用例全绿、`vue-tsc` 干净、`compileReleaseJavaWithJavac` 通过，
测试包 HppMusic-test.apk（sha256 a525883d…2f8fc）。

**追加**：预置深度 3 → 1（用户明确"不要预存"）。现在原生里只有"当前 + 下一首"，
且这个预置**只服务于 EOF 无缝换曲**：手动上下首、随机落点都由渲染层决定，
不再读原生窗口。深度改成 1 后切歌行为不变，只是极端情况下少了缓冲。
顺手把常量 `export` 出去，测试断言改成跟随常量（否则每次调深度都要改测试）。

## 全面排查："播放关键动作由 JS 定时器驱动"这一类问题

判定标准：**凡是用"等 N 毫秒"表达"N 毫秒后允许做什么"，后台节流一开就不等价。**
统一改成时间戳比较 + 把判定挂到原生 250ms 的 tick（`positionTicker`）上。

**已改**
1. `recentSeekIgnoreEnd`（布尔 + setTimeout 复位）→ `recentSeekIgnoreEndUntil`（时间戳）。
   影响：后台 seek 后 60 秒内所有 EOF 被当假结束吞掉 → "播完不切歌、原地停住"。
   改点：`state.ts` 字段、`player.ts` 换源恢复 1500ms、`playback.ts` dispatchSeek 800ms、
   `handleNativePlaybackEnded` 判断处、`adoptNativePlaybackSnapshot` 复位。
2. seek 合并窗口：定时器保留为前台快路径，新增 `flushPendingSeek(force)` 由 tick 调。
   `force` 是给定时器那条路径用的 —— 定时器可能比到期时间早一两毫秒触发，
   死抠时间戳会让它白等一轮 tick（这条被原有 seek 测试抓到过）。
3. 卡死恢复的自动下一首：`autoNextDeadline` + `flushAutoNext(force)`，同样双通道。
4. 睡眠定时器：tick 里也调 `sleepTimer.tick()`（该函数幂等：deadline 为 null 或
   已完成时直接返回）。

**没改，理由要记住**
- EOF 6 秒兜底看门狗（`mobile/adapters/player.ts:97`）**改不了**：EOF 之后
  `positionTicker` 只在 `isPlaying()` 时发 tick，停了就没 tick，它只能靠定时器。
- `player.ts:1708` AudioTrack 失败后 400ms 重开：故意等的延迟 + 罕见错误路径。
- 无缝预取过期、排队下一首 10s 加载超时：都是超时保护（失败方向），拖后只晚点放弃。
- `player.ts:491` 等 duration 的 10×50ms 轮询：原生一报时长就退出，通常首轮走。
- 桌面端 `bridge/audioPlayer.ts` 的 setInterval 淡入：Electron 没有对应原生斜坡。

**验证**：101 用例全绿、`vue-tsc` 干净；diff 用 `--numstat` 复核过没有整文件换行翻转；
APK sha256 39d55164…11619。

## MuMu 实测真相：通知栏切歌走了 MediaSession 播放器命令，且后台只暂存不推送

用户报"后台通知栏切歌只在两首之间来回"。连 MuMu（adb 端口 **7555**，不是常见的 16384）
实测，两个独立缺陷叠加：

### 1. 通知栏/车机的上下首不经过 onMediaButtonEvent

`dumpsys media_session` 日志里是 `reason=MediaSessionRecord:next`，`active item id`
在 **0/1 之间反复** —— 说明 SystemUI 调的是 `MediaController.skipToNext()`，
Media3 直接落到 ExoPlayer 的播放列表上，把原生那 2 项当成整个队列来回 seek。
`input keyevent KEYCODE_MEDIA_NEXT` 走的是另一条路（`onMediaButtonEvent`），所以
用按键测是好的、用通知栏测就坏 —— 这正是之前判断失误的原因。

修：`MediaSession.Callback.onPlayerCommandRequest` 拦 `COMMAND_SEEK_TO_NEXT/PREVIOUS`
（含 `_MEDIA_ITEM` 变体），返回 `RESULT_ERROR_NOT_SUPPORTED` 阻止它动播放器，
同时 `emitMediaControl("NextSong"/"PreviousSong")` 交回渲染层。

### 2. 后台的媒体按键只暂存、不推给 JS（"切不了歌"的真凶）

```java
if (appInBackground) { pendingMediaControls.addLast(...); return; }   // 旧实现
```
注释理由是"后台 WebView 可能完全不调 JS"——**这个前提是错的**：Chromium 节流的只有
setTimeout/setInterval，原生 tick 和 Capacitor 的 `evaluateJavascript` 照常执行。
日志实测：后台点通知栏"下一首"，`后台媒体按键已暂存: NextSong` 打出来，JS 全程没收到，
要等回到前台才补跳。

修：`emitMediaControl` 一律 notifyListeners，后台**额外**再入队做兜底；
入队去重靠 `sourceSeq`（JS 处理过就会换曲 → seq 变 → drain 时丢弃），
`NativeTrackTransition` 不入队（回前台会多一次无意义 reconcile）。

### MuMu 实测结果（修复后）
后台点通知栏下一首三次：九张机 → Unstoppable → Far Away From Home，三首各不相同，
`active item id` 不再 0/1 反复。APK sha256 41c371a3…00dbb。

### 环境坑
- MuMu 的 adb 端口是 **127.0.0.1:7555**；16384 是旧版/别的模拟器。
- 每个 Bash 调用结束时 adb daemon 会被回收，必须**在同一个 shell 里**完成
  connect → 操作 → 截图，且所有命令加 `-s 127.0.0.1:7555`（否则报
  "more than one device/emulator"）。
- SystemUI 的媒体卡片会随进度条宽度改变布局，`input tap` 容易点到进度条上；
  想确认是不是点到了按钮，看 logcat 有没有 `reason=MediaSessionRecord:next`。

## MuMu 复查：后台切歌其实是通的，链路全绿

加了 JS↔原生边界日志（`EchoBridge` tag）后实测两次：
- 刚切后台 16 秒按通知栏下一首 → `notifyListeners mediaControl=NextSong background=true`
  → 568ms 后 `JS -> load`，换歌成功
- **后台等 400 秒**再按 → 同样 `notifyListeners` + 550ms 后 `JS -> load`，换歌成功

结论：**JS 后台没有被冻结**（Chromium 节流只影响 timer，`evaluateJavascript` 照常执行），
所以"后台切不了歌"不是事件没送到。之前 02:39 那次失败没留日志，无法回溯；
当时累计了 11 条 stale 的 pending 记录，猜测是某次取链失败后的状态残留。

新增的两条日志（建议长期保留，是这个链路唯一的观测点）：
- `EchoBridge: notifyListeners mediaControl=<type> background=<bool>`
- `EchoBridge: JS -> load requestId=<n> host=<scheme>`

另一条经验：**这份 Java 文件是 CRLF**，用 python 脚本做字符串替换时
（`newline=''` 读出的是 `\r\n`）三引号里的 `\n` 匹配不上，替换静默失效、
mtime 变了但内容没变 —— gradle 因此判定 up-to-date，白等一次构建。
改 Java 一律用编辑工具，别用 python 批量替换。

## 通知栏"下一首"按钮消失 → 不能用 onPlayerCommandRequest 拒绝

用 `onPlayerCommandRequest` 返回 `RESULT_ERROR_NOT_SUPPORTED` 拦上下首，
**副作用**：Media3 会把 COMMAND_SEEK_TO_NEXT 从该控制器的可用命令里摘掉，
SystemUI 直接把"下一首"按钮隐藏 —— 按钮都没了，用户报"通知栏没有下一首按钮"。

改成在**播放器层**拦：新增内部类 `NavigationGuardPlayer extends ForwardingPlayer`，
传给 `MediaSession.Builder`。命令照常"被接受"（可用命令不变），但
`seekToNext/seekToPrevious`（含 _MEDIA_ITEM / _WINDOW）由它接住转给渲染层，
不落到 ExoPlayer 上。

**还有第二层原因**：按钮会时有时无。`clearBackgroundQueue` 会瞬间清掉预置的
"下一首"，列表只剩当前项 → ExoPlayer 的 `getAvailableCommands()` 没有
SEEK_TO_NEXT → Media3 重算 PlaybackState → SystemUI 藏按钮。
所以 `NavigationGuardPlayer.getAvailableCommands()` 里**恒声明**这六个命令
（上下首本来就由渲染层执行，与原生列表里有没有下一项无关）。

MuMu 实测：按钮常驻，连点两次都正确换歌（JS `load` requestId 4 / 6）。
APK sha256 d227905e…98869。

  PlaybackState 的 `actions=` 位掩码才是准的（SEEK_TO_NEXT = 0x100）。

## 后台挂久了切不了歌：Capacitor 的 native→JS 事件通道在后台 5 分钟后断投

**现象**：App 退到后台约 5 分钟后，通知栏/车机切歌无反应，自动播完也不切下一首。
回前台后积压的按键会一次性补跳。

**排查过程（关键证据）**：
1. 加 JS 心跳（`timeUpdate` 里每 30s 打一行 `hb tick=…`）。后台 4m47s 后心跳消失，
   与 Chromium「隐藏页 5 分钟」阈值吻合，一开始误判成页面被 frozen。
2. 但 `isFrozen=false`、`cgroup.freeze=0`、`curProcState=FGS`，进程根本没被冻结。
3. 决定性一击：在 `onMediaControl` 里加 `evaluateJavascript` 探针 →
   `唤醒前探针 value="hidden:…" 耗时=1ms`，**页面在跑 JS**。
4. 而同一时刻 `notifyListeners("mediaControl")` 送出的消息 JS 完全收不到。

**根因**：`Plugin.notifyListeners` → `MessageHandler.sendResponseMessage` →
`javaScriptReplyProxy.postMessage(...)`（WebMessageListener 通道）。App 退到后台
约 5 分钟后这条通道不再投递；`evaluateJavascript` 一直可用。音频在原生侧继续走，
所以表现成"在放，但按键/进度/换曲全哑"。

**修复（全事件走双通道）**：
- `EchoNativePlayerPlugin`：新增 `emit(event, payload)` —— 加单调 `__seq` →
  `notifyListeners`（前台官方通道）+ `dispatchByEval`
  （`window.dispatchEvent(new CustomEvent('hpp:native',{detail:{event,data}}))`）。
  9 个事件全部改走 `emit`：timeUpdate / durationChange / seeked / seekStateChange /
  stateChange / playbackEnd / fileLoaded / error / mediaControl。
- `nativePlayer.ts` 的 `listen()`：除 Capacitor 的 `addListener` 外，额外监听
  `hpp:native`，按 `__seq` 去重（两条通道都可能到达，seq 保证只处理一次）。
- 后台时 `tryWakeRenderer()` 仍保留（`onResume`+`resumeTimers`），真机若真的被冻结
  还有一层保险；实测 MuMu 上无副作用。

**验证（MuMu，后台 8 分钟）**：
- 心跳从 04:13 一直到 04:16 连续不断（修复前后台 4m47s 就断）；
- 04:14:12 自动切歌的 `NativeTrackTransition` 在后台被 JS 收到，tick 归零继续；
- 04:16:37 按通知栏下一首 → 20ms 后 `next: mode=random …` 立即执行。
- 101 个单测全绿，`vue-tsc` 干净。

**这意味着 `BACKGROUND_QUEUE_AHEAD` 不再决定"后台能播多久"**：tick 恢复后
`prepareBackgroundNext`（距结尾 90s 触发）在后台照常补窗口，深度只影响无缝程度。

### 方法教训
- **不要 `logcat -c`**：用户刚复现完的证据就在缓冲区里，清掉就再也拿不回来。
  长测前先 `logcat -d > 备份`，再清。
- 判断"页面/进程是否被冻结"要看三处：`/proc/<pid>/status State`、
  `/sys/fs/cgroup/uid_*/pid_*/cgroup.freeze`、`dumpsys activity processes` 的
  `isFrozen`；只看"日志不动"会误判。
- 区分"通道断"和"进程死"最快的办法：加一条 `evaluateJavascript` 探针带回调，
  回调里的耗时能直接说明 renderer 是否在跑。

## 第二层：后台 5 分钟后页面不再跑"任务队列"（定时器/网络回调全停）

修好事件通道后继续长测（MuMu，后台 7~8 分钟），发现按键能进 JS，但切歌卡在取链：

```
04:30:55  next: mode=random track=…           ← handler 立刻跑了
04:30:55  pt:resolve:start id=29860450        ← 取链开始
（25 秒后仍无 pt:resolve:done）
```

分层探针（`probeBackgroundLayers()`，通过 `EchoJS` 回传）：

| 后台时长 | plugin-call | fetch |
|---|---|---|
| 3m39s | ok（11ms） | ok 200（65ms） |
| 7m02s | **ok（36ms）** | **无响应** |

结论：**页面只执行同步的 `evaluateJavascript`，不再跑宏任务队列。**
- 插件调用响应走 legacy 桥 = `webView.post(evaluateJavascript)`，是 UI 线程的任务，
  promise 当场 resolve，所以**照常可用**；
- `fetch`/XHR 的响应是网络栈投递到页面的任务 → 不执行，Promise 永远 pending；
- `setTimeout` 同理（之前"定时器节流到 1/分钟"其实也是这个）。

所以：**后台能收到按键，但取链（HTTP）完不成 → 仍然切不了歌。**
`capacitor.config.ts` 已加 `android.useLegacyBridge: true`（事件通道修复，已验证）。

### 下一步（唯一可行方向）
把 HTTP 也搬到原生（CapacitorHttp / 自定义原生请求方法），让响应走同一条
`webView.post(evaluateJavascript)` 回来 —— 那条路后台是通的。待验证：
`CapacitorHttpAndroidInterface.isEnabled()` 是否真的把 `window.fetch` 打了补丁
（探针里 fetch 在 7 分钟时无响应，说明补丁没覆盖或没生效）。

## 最终解：用一条听不见的 WebAudio 保活，让页面不被 Chromium 冻结

第二层的原因确认是 **Chromium 对隐藏页面的 5 分钟冻结**（不是我们的 bug，也不是
Capacitor 的 bug）：页面被判定为"静默隐藏"后进入 frozen，定时器与网络回调全部停摆，
但原生主动 `evaluateJavascript` 仍能同步执行 —— 所以现象是"按键进得来、取链出不去"。

Chromium 不冻结**正在出声**的页面。本 App 的声音在原生 ExoPlayer，页面本身静音，
于是被当成静默页冻掉。

**实现**（`src/mobile/utils/backgroundKeepAlive.ts`，在 `mobile/main.ts` mount 后安装）：
- 页面加载时建一个 `AudioContext`（无需手势，实测 `state=running`）；
- 常驻一个 20Hz 振荡器（低于人耳下限），前台增益 0、切后台改成 0.02；
- 增益必须非 0，否则电平监控判成静音，等于没保活。

**验证（MuMu，后台 8 分钟）**：
- 后台 7 分钟后 `probe:fetch:ok 200`、`probe:xhr:ok 200`（保活前同一时刻两个探针都没有回调）；
- `pt:resolve:done url=y` → `api:done /search/lyric 65ms status=200` → `next: done`；
- `dumpsys media_session` 确认切歌后 `state=PLAYING`、position 正常推进。

### 完整的三处改动（缺一不可）
1. `capacitor.config.ts` → `android.useLegacyBridge: true`：原生→JS 事件在后台继续投递；
2. `backgroundKeepAlive.ts`：页面不被冻结，网络/定时器在后台继续工作；
3. 事件 `emit()` 双通道 + `__seq` 去重（`EchoNativePlayerPlugin` / `nativePlayer.ts`）：
   legacy 桥之外的兜底，去重表必须是**模块级**的（`setMediaSessionHandlers` 可能注册多次，
   放闭包里会导致一次按键跳两首）。

### 副作用与代价（要观察）
- 后台会一直有一条音频输出流（20Hz/0.02），耗电略增；人耳听不到，但真机要确认没有底噪。
- 若某些机型把 WebAudio 也判静音，这条会失效 —— 兜底是预置窗口。

### 已验证：Web Lock **不能**替代静音音频保活

按 Chromium 文档“持有 Web Lock 是免冻结条件”，实测单页 WebView 无效：

```
07:15:32  keepalive:lock:acquired        ← 锁确实拿到了
07:23:36  pt:resolve:start id=527617699  ← 8 分钟后取链
（没有 resolve:done，和没有保活时一模一样）
```

原因在 Chromium 的实现：豁免要求这把锁与**其他非冻结页面/worker** 竞争
（Conservative Page Freezing 的原文是 "contends with another non-frozen page/worker"）。
单页应用没人来抢锁，因此不算数。**别再试这条路**，直接用静音振荡器。

音频方案的两个小改进（已合入）：
- 增益切换改成 50ms `linearRampToValueAtTime` 斜坡，避免硬切时扬声器“咔”一声；
- 前台保持增益 0（不 suspend 上下文：后台 resume 没有用户手势，可能被挂起，得不偿失）。
