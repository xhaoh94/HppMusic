# 2026-11-03

## 修两个播放问题：随机只覆盖十几首 / 车机上单曲循环且切不了歌

两个问题各自独立，但都落在「原生后台队列」这块。

### 问题 A：随机播放只在十几首里打转

**根因（可复现、已用单测锁定）**：`prepareBackgroundNext()` 的"已准备"标记
`backgroundQueuePreparedRequestSeq` 在 `adoptNativePlaybackSnapshot()` 里无条件
写回 `state.playbackRequestSeq`。而 `playbackRequestSeq` 只在 `playTrack()` 里自增，
原生切歌不改它 —— 于是标记永远命中，`prepareBackgroundNext` 再也不跑。
原生队列就固定在"当前 + 15 首"（`BACKGROUND_QUEUE_AHEAD = 15`）里被
`REPEAT_MODE_ALL` 无限循环，而 Js 层根本收不到 `ended`（ALL 下不进 `STATE_ENDED`），
也就没有任何机会重建窗口。

**修**：
1. `adoptNativePlaybackSnapshot`：`backgroundQueuePreparedRequestSeq = changed ? -1 : state.playbackRequestSeq;`
   —— 必须显式置 -1。只写"不赋值"没用，标记是序号，留着旧值照样命中（第一版就这么错了，被新加的单测抓到）。
2. `prepareBackgroundNext`：随机模式的候选从 `state.shuffleQueue`（整列表一轮乱序）取，
   不够 15 首再用列表顺序补齐；不再用 `nativeQueueCandidateIndices` 的"当前项之后连续 15 首"
   （那样列表后段永远进不了窗口）。
   ⚠️ `shuffleQueue` 是上一轮队列的索引，换歌单后要等 `resolvePlaybackNextTrack` 才重置，
   这里必须按当前 `list.length` 过滤越界索引，否则 `list[index]` 为 undefined。
   原地保留了 `if (!track) return false` 兜底。

### 问题 B：连车机 + 锁屏 → 单曲循环、按下一首没反应

**两个独立缺陷，症状会叠在一起**：
1. 车机 / 蓝牙控制器 / 系统媒体面板能通过 `MediaSession` 直接
   `setRepeatMode` / `setShuffleModeEnabled`，**完全绕开** `applyBackgroundPlaybackMode()`。
   被改成 `REPEAT_MODE_ONE` 后 `backgroundRepeatMode` 还是 3（界面还显示随机），
   我们自己也不会再纠正 —— EOF 永远不进 `STATE_ENDED`。
   → 加 `Player.Listener.onRepeatModeChanged` / `onShuffleModeEnabledChanged` 抢回控制权
   （值等于期望值时直接返回，`setRepeatMode` 的二次回调不会递归），并打
   `Log.w` 留证据，下次能直接从 logcat 判断是不是车机改的。
   期望值抽成 `desiredRepeatMode()`，与 `applyBackgroundPlaybackMode` 共用。
2. `skipNativeQueueTrack` 用 `player.getNextMediaItemIndex()`，**这个 API 带 repeat 语义**：
   `REPEAT_MODE_ONE` 下返回的是当前项（不是 `INDEX_UNSET`），旧代码据此 `seekTo` 同一首。
   原来那句 `if (nextIndex == C.INDEX_UNSET && backgroundRepeatMode == 1)` 是死代码，
   永远不成立。→ 改成 `nextIndex == UNSET || nextIndex == currentIndex` 时自己按
   `(current ± 1) % count` 兜底；只有顺序模式（0）在边界才 `return false` 交回渲染层。

**未修的残留**：JS 完全冻结时窗口补不上（最多撑 15 首后回到窗口开头）。
彻底解决要让渲染层能下发更大的窗口或让原生做懒取链，属于另一个量级的工作。

### 追加：BACKGROUND_QUEUE_AHEAD 15 → 3，划掉 App 改为停止播放

用户拍板：不要 15 首的窗口（他要的是全列表随机，深度不是范围），划掉 App 就该停。

- `BACKGROUND_QUEUE_AHEAD = 3`（原生列表共 4 项）。深度只管"一次提前解析几个地址"，
  不管随机范围；窗口每首歌按整列表乱序重建。
- `AndroidManifest.xml` 给 EchoPlaybackService 加 `android:stopWithTask="true"`：
  划掉任务卡片 = 停播放 + 撤通知，行为显式、不受 ROM 影响。
  之前默认 false，而 Media3 `MediaSessionService.onTaskRemoved`（反编译确认）只在
  「没在播」时才 `pauseAllPlayersAndStopSelf()`，正在放就留着 —— 用户实测"划掉就停"
  是 ROM 强杀进程，两说都对。
- 澄清了一个我自己讲糊的点：**锁屏/后台时 JS 并不会被"冻结"**。`timeUpdate` 是原生
  250ms 定时器经 `evaluateJavascript` 推的，Chromium 节流只掐 setTimeout/setInterval，
  掐不到它；前台服务也保证进程不被当成 cached 冻结。原生后台队列的真实理由是
  「无缝换曲（EOF 不等网络）」+「划掉 App 后没人能取链」，不是"防 JS 冻结"。
- 15 → 3 同时把 `tests/nativePlaybackRecovery.test.ts` 里随机用例的断言改成
  不依赖具体深度（否则调深度就要改测试）。

### 追加 3：手动切歌只在 4 首里循环（深度改 3 暴露的回归）

**根因**：`next()`/`prev()` 手动上下首原来先走 `engine.skipNativeQueueTrack()`，
在**原生窗口内** seek。深度 15 时窗口有 16 首，用户没察觉；改成 3 后就是 4 首循环。
而且这不只影响随机 —— 列表循环模式下窗口是 [k, k+1, k+2, k+3]，
按 4 次下一首会 wrap 回 k（重播当前曲）。原生窗口根本不该承担"决定下一首"的职责。

**修**：手动上下首（界面 + 耳机/车机按键）全部改走渲染层决策，原生队列只负责
自动推进（EOF 无缝换曲）。
- `next()`/`prev()` 删掉 `skipNativeQueueTrack` 捷径；
- 新增 `backgroundResolvedByTrack`（曲目 ID → 解析结果），窗口准备时和
  `backgroundResolvedSources` 一起填/一起清；手动切歌把命中项当 `preResolved`
  传给 `playTrack`，`fallbackOnPreResolvedFailure: true`（地址放久了失效就退回完整取链）；
- 原生侧 `onStartCommand` / `onMediaButtonEvent` 的 NEXT/PREVIOUS 一律
  `emitMediaControl(...)` 交回渲染层，不再先本地 seek。
  前提是 stopWithTask=true 之后 WebView 和 service 同生共死，能放就一定有 JS。
- Java `skipNativeQueueTrack` 现在没有任何调用点，保留是为了不破坏
  `skipQueueTrack` 插件 API，注释里写明了。

**测试坑**（3 个）：
1. fixture 的 engine mock 缺 `setPlaybackRate`/`applyTrackLoudness`/`reset`，
   logger mock 缺 `error` —— playTrack 走得深，缺一个就 TypeError。
2. `resolvePlaybackNextTrack` 首次调用会重置乱序轮次（shuffleSourceQueueId 为 null
   → 整个 shuffleQueue 清空重建），所以"先 seed shuffleQueue 再 next() 断言落点"
   是测不准的 —— 得先跑一次让队列就位，再断言第二次落点 = 队首。
3. 乱序队列是 0 基索引，fixture 列表是 a,b,c,s3..s19，索引 5 = 's5' 不是 's6'。

**验证**：101 用例全绿（新增"手动上下首走渲染层决策" + "随机手动下一首按乱序推进"），
`pnpm build` + cap sync + assembleRelease 通过，HppMusic-test.apk 已更新
（sha256 4f69a1b9…a18136）。
