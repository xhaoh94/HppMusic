## 只读排查：断网后「回前台也播不了、重启才好」（未改代码）

用户报告断网后通知栏空标题、回到 app 仍无法播放、退出重进才恢复。代码层面确认存在同类卡死缺陷：

- 根因不是网络栈坏，是**取链 HTTP 全链路无超时 → Promise 永不 settle → 播放状态停在 `phase='loading'` → 无复位入口**。
- 原生 CapacitorHttp：`HttpRequestHandler.java:390/420` 的 connectTimeout/readTimeout 来自 call 参数，而 `native-bridge.js:671-677` 的 payload 不带这两个字段 ⇒ HttpURLConnection 默认 0（无限）。
- JS 侧同样无超时：`server/util/request.js:172-183`、`apiBridge.ts:248-252`、`renderer/utils/request.ts:285`；`native-bridge.js:900/972` 的 callbacks 只在回传到达时删，XHR patch `636-733` 无 setTimeout 兜底。
- 状态机：`playback.ts:1637` 置 loading → `1685/1707` await resolveAudioUrl；复位只在 await 之后（complete/failPlaybackIntent、applyFailedPlaybackState）。`stateMachine.ts:110` 的 loading 闸门让 `audio.ts:90..195`、`player.ts:257/769/983`、`playback.ts:1118/1241/1491/2519` 全部早退，连 stall 自愈都被挡住。
- 回前台无复位：MainActivity 无 ConnectivityManager/NetworkCallback，Manifest 无 ACCESS_NETWORK_STATE；`EchoNativePlayerPlugin.handleOnResume` 只翻 appInBackground。
- 通知栏空标题：`EchoPlaybackService.java:742` 占位「未在播放」；`updateMetadata` 在 resolve 之后（playback.ts:1745），取链卡住就没人下发 metadata。
- 不成立：无失败缓存/黑名单/熔断；native 异常路径会 call.reject；v0.1.6 的 useLegacyBridge + WebAudio 保活只防消息不投递和页面冻结，防不住 native 请求本身 hang。
- 取证限制：MuMu 127.0.0.1:7555 拒绝连接，本轮无 logcat 佐证，需日志锤实「当时确实挂在这个 Promise」。

用户要求只排查不动代码，等其确认后再给修复方案。

## 修复（用户确认「那你改吧」，未提交未推送）

四处改动，均为本地最小侵入：

1. `src/bridge/apiBridge.ts`：新增 `withRequestTimeout`（Promise.race + 清 timer），`handleApiRequest` 包一层；普通请求 15s、二进制请求体（听歌识曲 320KB PCM）30s，超时返回 504。没改 `server/`（上游会覆盖）也没改 node_modules（Capacitor 的 XHR patch 完全忽略 `xhr.timeout`，设了无效）。
2. `src/renderer/stores/player/playback.ts` + `player.ts`：新增 `flushStalledLoading` / `scheduleLoadingWatchdog`，用现成的 `playbackIntent.startedAt`（此前只写不读），45s 仍 loading 就 `applyFailedPlaybackState()`。`playTrack` 与 `refreshCurrentTrack` 各挂一次；`timeUpdate` 里补一次幂等检查。**原生 tick 只在 `player.isPlaying()` 时发（EchoPlaybackService.java:143-151），卡 loading 时收不到，所以 JS 定时器是主路径，tick 只是辅助**。
3. `src/mobile/main.ts` + `player.ts` + `stateMachine.ts`：`installNetworkRecovery` 监听 `online` + `visibilitychange`，5s 去抖；store 新增 `retryFailedPlayback(): boolean`，只认 `shouldRetryFailedPlayback`（phase='failed' 且有曲目），先 `setPlaybackIntentPlayback(state,true)` 再 `refreshCurrentTrack()`，否则 failed 态会被当成暂停只取链不播。main.ts 用动态 `import('@/stores/player')`（`@` 指向 src/renderer，写 `@/renderer/...` 会 TS2307），boot-order 检查通过。
4. `EchoPlaybackService.java:updateMetadata`：title 空串时沿用 `pendingMetadata` 的上一次标题，不再落到「未在播放」占位。

测试：新增 `tests/apiRequestTimeout.test.ts`（5 例）、`tests/nativePlaybackRecovery.test.ts` 加 2 例 watchdog；该测试文件补了文件级 `beforeEach` stub window（node 环境无 window，playTrack 新增的 `window.setTimeout` 会让既有用例挂）。

验证：`vue-tsc` 0 错、`vitest run` 108/108、`npm run build`（含 check-boot-order）通过、`bash scripts/android-build.sh debug` BUILD SUCCESSFUL，APK `android/app/build/outputs/apk/debug/app-debug.apk` 8,184,017 B / 12:02。**真机断网复现尚未验证**，用户是手机真机出问题、模拟器不复现（模拟器断网会立刻 ENETUNREACH → native reject；真机 WiFi 连着无外网时 TCP SYN 无响应）。
